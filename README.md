# Прогнозирование объёмов отгрузок со складов

Проект по задаче прогноза объёмов отгрузок для маркетплейса на данных WB Space / WildHack.

## Кратко

Цель проекта — предсказать объём отгрузок по каждому `route_id` на горизонте 8 следующих получасовых интервалов и использовать этот прогноз для более точного вызова транспорта.

**Финальный результат:**
- public leaderboard: **0.336**
- лучшая локальная валидация: **0.332463**
- финальная модель: **multi-output Ridge**
- финальное окно обучения: **5 дней**
- постобработка: **clip negatives + global scale = 0.9975**

## Постановка задачи

Дано:
- маршрут `route_id`
- временная метка `timestamp`
- статусы обработки товаров `status_1 ... status_6`
- целевая переменная `target_1h`

Нужно предсказать объём отгрузок на тестовом горизонте для каждой строки тестового набора.

## Идея решения

Я перевёл задачу в **multi-horizon forecasting**:

- каждая обучающая строка соответствует моменту времени `source_timestamp`
- для неё формируются 8 целевых колонок:
  - `target_step_1`
  - `target_step_2`
  - ...
  - `target_step_8`

Таким образом, модель сразу предсказывает весь будущий профиль отгрузок на 4 часа вперёд с шагом 30 минут.

## Валидация

Ключевой акцент проекта — **локальная валидация, близкая к leaderboard-сценарию**.

Использованный backtest:
- валидация по нескольким историческим `cutoff`
- все `cutoff` выбраны на том же времени суток, что и финальный прогноз
- дополнительно используется тот же день недели (`same_weekday=True`)
- между train и valid выдерживается gap, равный длине горизонта прогноза, чтобы не допускать утечки будущих таргетов

Это позволило лучше согласовать локальный скор с публичным leaderboard и осознанно подбирать признаки и гиперпараметры.

## Признаки

### Финальный набор признаков
- `route_id`
- текущие статусы `status_1 ... status_6`
- `target_now`
- лаги таргета: `target_lag_1, 2, 4, 8, 48, 336`
- rolling-статистики таргета:
  - `target_roll_mean_*`
  - `target_roll_std_*`
- лаги статусов:
  - `status_*_lag_*`
- rolling-статистики статусов:
  - `status_*_roll_mean_*`
  - `status_*_roll_std_*`

### Что ещё пробовалось
- агрегаты статусов
- лаги и rolling агрегатов
- ratio / balance признаки
- календарные признаки источника и будущих горизонтов

По локальной валидации эти блоки не дали устойчивого прироста, поэтому в финальный конфиг не вошли.

## Модель

Использована **Ridge Regression** в пайплайне:

- `OneHotEncoder` для `route_id`
- `SimpleImputer(strategy="median")` для числовых признаков
- `StandardScaler`
- `Ridge(alpha=4.0)`

Почему Ridge:
- быстрый цикл экспериментов
- устойчивая работа на большом количестве лаговых признаков
- хороший базовый bias/variance trade-off
- удобно использовать как сильный линейный baseline для табличного временного ряда

## Эксперименты

Эксперименты велись последовательно:
1. базовый набор `route_id + status_*`
2. добавление `target_now`
3. лаги таргета
4. rolling по таргету
5. лаги статусов
6. rolling по статусам
7. отбор полезных/бесполезных блоков
8. подбор `alpha`
9. подбор длины train window
10. калибровка под целевую метрику

### Итог по экспериментам
- лучший прирост дали:
  - `target_now`
  - `target_roll_*`
  - `status_lag_*`
  - `status_roll_*`
- календарные признаки и более сложные агрегаты не улучшили итог
- оптимальное окно истории оказалось коротким: **5 дней**
- короткое окно уменьшило bias и лучше адаптировалось к недавнему режиму ряда

От базовой конфигурации до лучшей локальной модели метрика улучшилась с **0.354584** до **0.332463**, то есть на **0.022122** абсолютных пункта (~**6.2%** относительно базы).

## Метрика и калибровка

Соревновательная метрика:

`WAPE + |Relative Bias|`

Из-за отдельного штрафа за bias постобработка оказалась важной:
- отрицательные предсказания клипались в 0
- далее подбирался **global scale**
- финальное значение: **0.9975**

Отдельная калибровка по горизонтам локально давала чуть лучший скор, но была отброшена как более рискованная с точки зрения переобучения.

## Главные выводы

1. **Хорошая валидация важнее сложной модели.**
2. Для этой задачи короткая обучающая история оказалась лучше длинной.
3. Отдельный контроль bias критичен из-за целевой метрики.
4. Простая линейная модель может быть конкурентной, если правильно собрать признаки и аккуратно валидировать решение.
